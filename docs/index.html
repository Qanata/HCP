How it works

Architecture

One binary in the middle

hcp is a single executable. It is the API your agents call, the thing that talks to Slack, the scheduler that enforces deadlines, and the writer of your vault. The MCP server and the Claude Code hook are the same file, run with a different word after it.

Runs on your Mac

Installs as a launchd service. It starts at login, is restarted if it stops, and listens on localhost only unless you say otherwise.

Postgres holds the state

Requests, API keys and audit events live in Postgres. A state change and its audit record are written in one transaction, so neither exists without the other.

Obsidian holds the record

Each audit event is queued in that same transaction and then written to your vault. If the vault is unavailable the log falls behind and catches up. Entries are not lost.

Slack

Answered where you already are

There is no portal to keep open. Requests arrive in a Slack channel and you answer from your phone or your desk.

  • No public URL. hcp opens an outbound connection to Slack (Socket Mode), so a Mac behind a home router works as it is.
  • The message says what silence means. Every request shows its deadline and what happens then. If no answer means yes, that part is in bold.
  • Name a responder and only their click counts. Anyone else who presses a button is told, privately, why nothing happened.
  • Messages retire themselves. Once a request is answered, cancelled, escalated or timed out, its message is rewritten to say so and the buttons are removed.
What you get for each kind of request
The agent asks for In Slack
An approval Approve and Reject buttons
A clarification, decision, review, input or escalation A Respond button that opens a text box. Your words go back to the agent
Nothing; it is a notification Logged to the vault. Posted only if you name a channel for notifications
Vault

The audit trail is a folder of Markdown

The log lives in your Obsidian vault as plain notes you can search, link and query, next to everything else you keep there.

  • One note per request, with properties you can filter on: state, intent, urgency, agent, responder, decision, deadline.
  • An append-only daily log. Each line links to its request and ends in a block ID, so another note can point at one specific event.
  • Agent text stays inert. Whatever an agent puts in a request is written as plain text. It cannot plant links, tags, properties or plugin code in your vault.
  • Postgres is still the system of record. The vault is the copy you read.

Agents

Three ways for an agent to ask

All three end in the same place: a request in Slack and a record in the vault.

REST API

Post a request, poll for the answer. Anything that can make an HTTP call can use it, with an API key per agent.

MCP server

hcp mcp gives any MCP harness five tools. hcp_coordinate asks and waits for your answer; hcp_notify tells you something and moves on. It speaks every MCP revision from 2024-11-05 to 2026-07-28.

Claude Code hook

hcp hook sees every command before it runs, whether the agent wants it to or not. Nothing in the agent's prompt has to change.

How the hook sorts Bash commands
Tier For example What happens
Safe ls, git status, cat x | grep y Passes silently, without contacting the server
Notify cargo build, npm install, file edits Logged. Nothing waits
Gate rm -rf, git push, terraform apply, DROP TABLE Held until you approve it in Slack

The gate is a list of patterns for common destructive commands. It is a tripwire, not a sandbox: a determined agent can find a command it does not match.

By design

When it is unsure, it says no

An approval step that waves things through when something breaks is not an approval step. These are the cases hcp is built around.

An agent cannot approve itself

Answering through the API takes a key with a separate permission, one that agent keys are not given.

Nothing is approved unseen

If Slack could not deliver a request, it never counts as waiting on you, so an approve-on-timeout policy cannot fire on something nobody was shown.

A held command needs a person

A rejection, a timeout, a lost connection and an unreachable server all block it. Letting commands through when the server is down is a setting you have to turn on.

Clicks are authenticated

Button presses arrive over the connection hcp opened to Slack, or over HTTP with Slack's signature checked. Nobody can approve by guessing a URL.

Escalation ends

An unanswered request escalates once, to the person you named, with a fresh deadline. If they do not answer either, it times out.

Agents see only their own

An agent's key reads, cancels and collects answers for that agent's requests and nobody else's.

Install

Install on a Mac

You need a Rust toolchain, a Postgres database, an Obsidian vault and a Slack app. The installer builds the binary and sets it up as a background service.

  terminal
git clone https://github.com/Qanata/HCP && cd HCP

# Build and install. The first run creates ~/.config/hcp/hcp.env and stops there
deploy/macos/install.sh

# Fill in that file, then create a key for each agent
~/.local/bin/hcp --env-file ~/.config/hcp/hcp.env keys create claude-code

# Run the installer again to start the service
deploy/macos/install.sh

curl http://127.0.0.1:3100/health
  ~/.config/hcp/hcp.env
DATABASE_URL="postgresql://…"
HCP_OBSIDIAN_VAULT="~/Obsidian/Main"   # the vault folder; logs go under HCP/ inside it
SLACK_BOT_TOKEN=xoxb-…
SLACK_APP_TOKEN=xapp-…               # enables Socket Mode
HCP_SLACK_CHANNEL=C0123456789        # where requests are posted

Creating the Slack app, connecting Claude Code and MCP harnesses, and every setting are covered in the README.

API

A small REST API

Every /v1 endpoint takes Authorization: Bearer <key>. An agent's key works only on that agent's requests.

POST/v1/requestsSubmit a coordination request
GET/v1/requests/{id}Read one. Reading your answered request takes delivery of the answer
GET/v1/requestsList your requests, with filters
DELETE/v1/requests/{id}Withdraw a request
POST/v1/requests/{id}/respondAnswer one. Needs a key with the respond permission
GET/v1/auditAudit events
GET/v1/eventsState changes as they happen, over SSE
GET/healthHealth check
Lifecycle

Every request follows a defined lifecycle

A request is only waiting on you once it has actually been delivered. One that never reaches Slack goes straight from routing to timed out.

How a request ends

DELIVERED: answered, and the agent has the answer. TIMED_OUT: nobody answered, or it could not be delivered. CANCELLED: the agent withdrew it.

What happens at the deadline

The agent chooses when it asks: AUTO_REJECT, AUTO_APPROVE, ESCALATE to a second person, or simply time out (BLOCK, FAIL, SKIP).
